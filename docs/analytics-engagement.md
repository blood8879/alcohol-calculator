# Engagement analytics

All events pass through `logFirebaseEvent` and its collection consent gate. New engagement events contain only fixed labels, public quiz question IDs, booleans, or small progress indexes. They never include free text, custom drink IDs or names, drink quantities, price, weight, BAC, timestamps, backup content, or session records. Existing quiz, session, notification, goal, and challenge events use `utils/analytics.ts`; activity counts and durations are bucketed, and BAC-derived results are not logged.

| Journey | Events and firing semantics |
| --- | --- |
| Quiz | `quiz_category_selected` on category tap; legacy `quiz_started` on standard/daily start; `quiz_question_answered` once per question index with public ID, correctness, and elapsed time since quiz start bucket; legacy `quiz_completed` at final answer; `quiz_abandoned` once when an active attempt exits by Back or loses tab focus, with a coarse progress bucket; `quiz_restarted` when retry callback actually starts another quiz; `quiz_share_result` after share sheet returns. |
| Tracker | `tracker_add_opened` on modal opening, `tracker_add_mode_selected` on tab or preset choice, `tracker_add_validation_failed` for invalid input or storage failure, `tracker_add_saved` and legacy `drink_logged` only after storage confirms the write, `tracker_add_closed` on explicit close, `tracker_delete_intent` on delete tap, `tracker_delete_succeeded` only after storage confirms deletion. Quick-log chips emit `tracker_add_saved` with `source: "quick_log"` and `drink_logged` with `source: "quick_log"` after the write succeeds; their undo toast emits `tracker_delete_intent` / `tracker_delete_succeeded` with `surface: "quick_log_undo"`. Deleting a drink log is immediate (`surface: "drink_log"`) and shows the same undo toast; restoring the exact deleted log emits `tracker_add_saved` with `source: "undo_delete"` after storage confirms the write (no legacy `drink_logged`, since it is not a new drink). Custom drink save/delete events follow successful storage calls. |
| Live session | Legacy `session_started` after active session persistence; `session_resumed` when a saved session is loaded; `session_drink_added` or `session_drink_removed` after active session persistence; `session_discard_intent` before confirmation and legacy `session_discarded` after clearing; legacy `session_ended` and `session_save_succeeded` only after history persistence and active session removal. Drink logs and history deduplicate retries after a partial save. `session_start_validation_failed` fires when the start is blocked: `reason: "invalid_weight"` (empty, non-numeric or ≤ 0) or `reason: "weight_out_of_range"` (outside 30–250 kg, see `utils/bodyWeight.ts`). |
| Settings | `settings_permission_requested` before requesting notification permission and `settings_permission_outcome` after its result; `settings_preference_saved` and legacy `notification_toggled` only after preference persistence; `language_changed` after changing to a different language; `backup_export_outcome` and `backup_restore_outcome` report only result labels. |
| Goals and sharing | Legacy challenge/goal events fire after storage success; `challenge_stopped` and `weekly_goal_cleared` follow successful removal; share outcome events report result labels. Session history deletion distinguishes intent and successful persistence. |

An app kill cannot be observed reliably, so `quiz_abandoned` describes only Back and navigation or tab focus loss. A mounted quiz may still be resumed after focus loss; its completion remains valid, and the attempt is not counted as abandoned again. Share sheet return does not prove the recipient received the content. Session and tracker persistence are local storage outcomes, not cloud backup guarantees.
